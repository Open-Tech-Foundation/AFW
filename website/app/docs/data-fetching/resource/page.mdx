# `resource()`

For client-side async data, `resource()` formalizes the fetch-into-signals
pattern — components stay synchronous, and the view renders the resource's
reactive states:

```jsx
import { resource, router } from "@opentf/afw";

export default function UserProfile() {
  const user = resource(
    () => router.params.id, // reactive source — re-fetches when it changes
    async (id, { signal }) => {
      const response = await fetch(`/api/users/${encodeURIComponent(id)}`, { signal });
      if (!response.ok) throw new Error(`Request failed: ${response.status}`);
      return response.json();
    },
  );

  return (
    <div>
      {user.error ? <p>Failed: {user.error.message}</p> :
       user.loading ? <p>Loading…</p> :
       user.data ? <h1>{user.data.name}</h1> : <p>No user selected.</p>}
    </div>
  );
}
```

- `resource(fetcher)` fetches once; `resource(source, fetcher)` re-fetches when
  the reactive `source` changes; `{ initial }` seeds `data`.
- Each run aborts the previous run's `AbortController` (the fetcher receives
  `{ signal }`) and late, out-of-order resolutions are discarded.
- A rejection sets `error` and keeps the last good `data`; the next success
  clears it.
- `refetch()` re-runs manually. It resolves with the new data and rejects when the
  fetch fails, so `await user.refetch()` can be wrapped in `try`; a click handler can
  ignore the promise, since the failure also shows on `error`.
- A `source` returning `null`/`false` pauses fetching (conditional resources).
- [`invalidate()`](/docs/server-functions#refetch-after-an-action) refetches every live
  resource and reloads the page's loader data; `invalidate(listTodos)` only the
  resources that called that server function.
- During SSG/SSR nothing fetches and `loading` stays `true` (`false` when the source
  starts paused), so the prerendered HTML shows the branch the browser's first paint
  shows and [hydration](/docs/deployment/hydration) stays aligned.
- A resource created in a component stops when the component is removed: its fetch
  is aborted and it no longer refetches.
- `{ errors: "inline" }` keeps failures on `error` only, even inside a
  [`<Pending>`](/docs/data-fetching/pending).

## Caching

A resource whose fetcher is a [server function](/docs/server-functions), or that names
a `key`, keeps its result in a page-wide cache:

```jsx
import { resource, router } from "@opentf/afw";
import { getUser, listTodos } from "./users.server.js";

// Cached by the server function and its input.
const user = resource(() => ({ id: router.params.id }), getUser);
// A server function without input.
const todos = resource(listTodos);
// Any other fetcher: name a key (a value, or a function of the source value).
const repo = resource(() => router.params.name, fetchRepo, {
  key: (name) => ["repo", name],
  staleTime: 30_000,
});
```

- **Shared requests.** Every resource showing the same call or key shares one request
  and the same data. A refetch in one updates all of them.
- **Instant remounts.** A remounted resource shows the cached data at once, so a
  `<Pending>` shows the content (with its `refreshing` view) instead of the fallback.
- **`staleTime`** (default `0`): how long cached data answers without a request. At `0`
  the cached data shows and is revalidated at once.
- **`gcTime`** (default 5 minutes): how long an entry nothing shows is kept.
- **Keys.** A server function's key is its endpoint and input. Object key order does not
  matter: `{ a, b }` and `{ b, a }` are one entry.
- **Shared data.** Every user of an entry gets the same object: treat it as read-only.
- **Direct calls.** Identical query calls in flight share one request too
  (`Promise.all([listTodos(), listTodos()])` makes one). Actions never do.
- **Aborts.** A shared request is aborted only once every resource or caller using it
  has aborted or unmounted.
- `refetch()` and `invalidate()` always ask the server, whatever the `staleTime`.
- **On logout**, call `clearQueryCache()`. `invalidate()` keeps showing the stale data while
  it refetches, which would show the previous user's data to the next one.
  `clearQueryCache()` removes it:
  - nothing is left to show on a remount;
  - requests in flight write nothing;
  - mounted resources that used it go back to loading (and their `<Pending>` to its
    fallback) and fetch again.
  - `clearQueryCache(getTodo)` or `clearQueryCache(getTodo, { id })` clears only those calls.

```js
import { clearQueryCache } from "@opentf/afw";

async function logOut() {
  await signOut();
  clearQueryCache();
}
```
- After an action, the [single-flight `refresh()`](/docs/server-functions#update-in-the-same-request)
  updates cached calls in the action's own response.
- A fetcher that calls a server function inside it (`() => listTodos({ done })`)
  shares requests too. It shows cached data at once only when written as
  `resource(source, listTodos)` or given a `key`.

## Resilience

```jsx
const feed = resource(() => ({ page }), listPosts, {
  timeout: 8_000,
  revalidateOn: ["focus", "online"],
  staleTime: 60_000,
});
```

- **Retries.** A server function query whose request never reached the server
  (offline, a dropped connection) is retried twice, after 300 ms and 1 s. An HTTP error
  is the server's answer and is not retried. Actions are never retried.
- **`timeout`** (ms): a run that takes longer is aborted; `error` is a `TimeoutError`.
- **`revalidateOn`**: `"focus"` refetches when the tab becomes visible again, `"online"`
  when the browser reconnects. It skips data younger than `staleTime`. Off by default.

## Recipes

### Prefetch

A query call fills the cache, so call it before the view needs it:

```jsx
<a href={`/todos/${todo.id}`} onpointerenter={() => getTodo({ id: todo.id })}>{todo.title}</a>
```

- The resource on the next page shows the data at once. Give it a `staleTime` to skip
  the revalidation request too.

### Pagination and infinite scroll

```jsx
// Pages: the previous page stays shown while the next one loads.
let page = $state(1);
const posts = resource(() => ({ page }), listPosts);

// Infinite scroll: one component per loaded page, each with its own resource.
function PostPage({ page, last, onmore }) {
  const posts = resource(() => ({ page }), listPosts);
  return (
    <>
      {(posts.data ?? []).map((post) => <PostCard key={post.id} post={post} />)}
      {/* After the last page loads: ask for more while the end is in view. */}
      {last && posts.data?.length > 0 && <Sentinel onvisible={onmore} />}
    </>
  );
}

// Calls `onvisible` whenever it is in view, including when it mounts in view.
function Sentinel({ onvisible }) {
  onVisibilityChange((visible) => visible && onvisible());
  return <div aria-hidden="true" />;
}

export default function Feed() {
  let pages = $state(1);
  const numbers = $derived(Array.from({ length: pages }, (_, i) => i + 1));
  return (
    <section>
      {numbers.map((n) => <PostPage key={n} page={n} last={n === pages} onmore={() => pages++} />)}
    </section>
  );
}
```

- `key={n}` keeps loaded pages mounted as pages are added, so they are not fetched again.
- Each page is its own cache entry, so remounting the feed shows it at once.
- The sentinel renders only once the last page has data. It mounts fresh each time, so
  [`onVisibilityChange`](/docs/macros) reports it at once when it is already in view, and
  loading continues until the screen is full. An empty page ends the feed.
- A "Load more" button can replace the sentinel: `onclick={onmore}`.

### Polling

```js
onMount(() => {
  const id = setInterval(() => todos.refetch(), 10_000);
  return () => clearInterval(id);
});
```

- For data the server pushes, prefer server-sent events or a WebSocket with
  `setQueryData`.
