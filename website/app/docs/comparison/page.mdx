# Comparison

This page compares AFW with the frameworks it is most often weighed against:
**Next.js**, **TanStack Start**, **React Router** (framework mode, the successor of
Remix), **Nuxt**, **SvelteKit**, **Astro** and **SolidStart**. It covers what each one
gives you out of the box, and it is explicit about where AFW is behind.

<Callout type="info" title="Checked November 2026">
  Versions compared: Next.js 16, TanStack Start 1.0, React Router 7, Nuxt 4,
  SvelteKit 2, Astro 6, SolidStart 2, and AFW's next release. Frameworks move quickly;
  each one's own documentation is the authority on its current features. Runtime and
  build-speed numbers are on [Benchmarks](/docs/benchmarks), not here.
</Callout>

- 🟡 Partial, experimental, or through an official add-on.

## Where AFW differs

- **Components are web standards.** Each one is a real `HTMLElement`. There is no
  framework runtime to mount and no virtual DOM to reconcile: the Rust compiler emits
  the DOM operations each view needs, and each `{expression}` binds to the signal it
  reads.
- **Islands without opting in.** Because every component is its own element, each
  adopts its server-rendered DOM on its own. Astro offers this as an explicit model;
  in AFW it is how hydration works.
- **Two toolchains, one app.** The same `app/` folder builds with
  [esdev and ES-Runtime](/docs/getting-started/installation) — a single binary with a
  capability-secured server runtime — or with Vite and Node, for server code that
  needs the Node ecosystem.
- **More of the stack is first-party.** Forms, i18n, component testing and a
  documentation theme with search, feeds and `llms.txt` ship from the same project,
  versioned together.

## Where AFW is behind

AFW is alpha. Compared with the frameworks above it does not yet have:

- **Complete server functions** — AFW has typed `query()` / `action()` calls and
  `invalidate()`, but not yet forms that submit without JavaScript or single-flight
  updates, which Next.js, React Router, SvelteKit and SolidStart provide.
- **Streaming server rendering** — pages render to one complete HTML string, and
  loaders finish before rendering starts.
- **Richer loaders** — layout loaders and redirects from a loader.
- **Routing conventions** — route groups, optional segments, per-route error and
  loading files, and fully type-checked routes in the style of TanStack Router.
- **Navigation polish** — view transitions.
- **Image optimization**, and **cached or incremental regeneration**.
- **Ecosystem and maturity** — none of the others is new, and React, Vue and Svelte
  each come with a large library ecosystem AFW cannot match yet. APIs can change
  between minor versions.

The [roadmap](https://github.com/Open-Tech-Foundation/afw/blob/main/docs/roadmap.md)
tracks these.

## Choosing

**Next.js** — you want React with Server Components, a caching model built into the
framework, and the largest ecosystem and hosting support. AFW has no server
components and no data cache.

**TanStack Start** — you want React (or Solid) with end-to-end type safety: typed
routes, search params and server functions. AFW's routes and params are not type-checked
across the app, though its server functions are typed against their real signatures.

**React Router** — you want the Remix model in React: loaders, actions and progressive
enhancement, with a gradual path from a client router. AFW has loaders and actions,
but its actions need JavaScript.

**Nuxt** — you want Vue, a large module ecosystem, and Nitro's deployment presets.

**SvelteKit** — you want a compiled, fine-grained framework with its own component
syntax and mature form actions. AFW is closest to it in rendering approach, with JSX
and Custom Elements instead of `.svelte` files.

**Astro** — your site is mostly content and you want to mix UI frameworks or ship no
JavaScript by default. AFW is a single-framework alternative with built-in docs and
blog support.

**SolidStart** — you want Solid's signals and JSX, which are the closest to AFW's
model; SolidStart has server functions and streaming today.

**AFW** — you want components that are web standards, fine-grained updates with no
virtual DOM, and first-party forms, i18n, testing and docs, and you can work with an
alpha framework while the gaps above close.
