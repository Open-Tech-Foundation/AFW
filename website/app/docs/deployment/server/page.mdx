# Server Setup

API routes, middleware, loaders and server functions are standard server modules. The
AFW plugin composes them into one Fetch handler, `@afw/server`; a server entry hosts it.

## The generated server module

The AFW plugin generates `@afw/server` from `app/`, in both workflows:

- `createHandler({ files, renderPage, fallback })` — one Fetch handler. Inside the
  app's middleware it answers API routes, [server functions](/docs/server-functions)
  and loader data (`<path>/__data.json`), then `files(request)`, then
  `renderPage(request)`; each may return `null` to pass. `fallback` answers the rest.
- `createPageRenderer({ shell })` — with `mode: "ssr"`: renders pages per request into
  `shell` (the client's `index.html`), with loader data, metadata and hydration.
- Also exported: `apiRoutes`, `middleware`, `loaders`, `serverFunctions`, and `render`
  (with pages) for custom pipelines.

**Vite + Node** — nothing to write: `vite build` emits `dist/server/index.js`, which
serves the client, answers the app's server code and renders pages. For your own
server, import `createHandler` from `dist/server/app.js`.

**esdev + ES-Runtime** — the app owns its server entry, a server target:

```js
// server.js — the server target's entry
import { serve } from "runtime:http";
import { file } from "runtime:fs";
import { env } from "runtime:process";
import { createHandler, createPageRenderer } from "@afw/server";

// Beside this bundle: dist/ in production, .dev/dist/ under `esdev start`.
const outDir = new URL("./", import.meta.url);

async function files(request) {
  const { pathname } = new URL(request.url);
  if (pathname === "/" || pathname.endsWith(".html")) return null; // pages render below
  const asset = file(new URL(`.${pathname}`, outDir));
  if (!(await asset.exists())) return null;
  const type = { js: "text/javascript; charset=utf-8", css: "text/css; charset=utf-8" }[pathname.split(".").pop()];
  return new Response(asset.stream(), { headers: { "content-type": type ?? "application/octet-stream" } });
}

const shell = await file(new URL("./index.html", outDir)).text();
const handle = createHandler({
  files,
  renderPage: createPageRenderer({ shell }), // with mode: "ssr"; leave out for an SPA
  fallback: () => new Response("Not Found", { status: 404 }),
});
serve({ port: Number(env.PORT ?? "3000") }, handle);
```

```json esdev.json
{
  "plugins": [{ "module": "@opentf/esdev-plugin-afw", "options": { "mode": "ssr" } }],
  "build": { "targets": {
    "web": { "entry": "index.html", "outdir": "dist" },
    "server": { "entry": "server.js", "out": "dist/server.js" }
  } },
  "dev": { "run": "server", "app": { "port": 3000 } }
}
```

- `esdev start` runs the `dev.run` target and restarts it when server code changes.
- `esdev build`, then `esdev dist/server.js`, for production.
- Server builds resolve page imports through the DOM-free `@opentf/afw/server` entry,
  so no `HTMLElement` stub is needed.

## Register pages by hand

For a pipeline the generated module does not cover, the pieces are public:

```js
import { registerRoutes, renderRoute } from "@opentf/afw/server";
import { pages } from "@afw/routes";

registerRoutes(pages);

export async function renderPage(request, data) {
  const url = new URL(request.url);
  return renderRoute(url.pathname, null, url.search, { data });
}
```

- `renderRoute` returns HTML, metadata, hydration props and status; each call isolates
  route values and island props across async work.
- During rendering, `router.params`, `router.query`, `router.locale` and `router.data`
  refer to the current request.
- See [Metadata & SEO](/docs/routing/metadata) for head rendering and the
  [Server API](/docs/server) for `createApiHandler`, `createLoaderRegistry` and
  `createMiddleware`.

## Other runtimes

For Fetch-native platforms, `createFetchHandler` composes dispatch and middleware
with a fallback for assets or SSR. When your build script emits `dist/server/api.js`,
see [Fetch handler](/docs/deployment/fetch-handler) for adapter wiring.

Node applications import `toNodeListener` from `@opentf/afw/server/adapters/node`.
Keep runtime-specific imports in the server entry, not in client components.

## Environment and server-only imports

On ES-Runtime, read variables from `runtime:process`'s `env`. Other hosts expose
variables through their own environment API, and Fetch platforms can pass bindings
as `context.env`/`context.ctx`. Configure environment loading for your chosen host;
the retired CLI's automatic Bun `.env` loading is not part of esdev integration.

Keep database clients and secrets in `loader.*`, `route.*`, `_middleware.*` and
server entries. The compiler does not provide a guarantee that arbitrary imports
placed in client components stay server-only.

See [API Routes](/docs/routing/api-routes), [Middleware](/docs/routing/middleware)
and [Data Fetching](/docs/data-fetching).
