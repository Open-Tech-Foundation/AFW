# Docs Configuration

## Site config

Site-wide options live under `docs` in `afw.config.js` — brand, version, GitHub
link, and the top-level nav (which supports per-link icons).

The package includes TypeScript declarations for configuration, components, and
generated navigation and blog data. For a custom configuration object, import
`DocsConfig` or `SiteConfig` with `import type` from `@opentf/afw-docs/config`.
`defineDocsConfig` checks the supported options and preserves the supplied shape.

```js
import { defineDocsConfig } from "@opentf/afw-docs/config";

export default defineDocsConfig({
  docs: {
    title: "AFW",
    version: "v0.16.0",
    logo: "/logo.png",
    github: "https://github.com/Open-Tech-Foundation/afw",
    // Source repo — edit links also need lastUpdated's source-path data.
    repoUrl: "https://github.com/Open-Tech-Foundation/afw",
    nav: [
      { label: "Home", href: "/" },
      { label: "Docs", href: "/docs" },
    ],
    // Foot of every docs/API page: git-derived "Last updated" + GitHub edit link.
    lastUpdated: true,
  },
});
```

## The sidebar tree

The `afwDocsPlugin` build plugin (see [Build plugins](#build-plugins)) generates the
sidebar data from a `docs` block.

The sidebar is generated from the folder tree under your docs directory. A folder
with a `page.*` becomes a link; a folder **without** one becomes a group subheading
over its children. Nesting is arbitrary.

Parameterized folders such as `[slug]` and `[...path]`, including their descendants,
are omitted from automatic navigation. `getStaticPaths()` enumerates prerendered
URLs; it does not populate the navigation tree. Link to concrete generated URLs
from your documentation content.

Each folder's `_meta.js` sets the order and labels of its children. Listed keys come
first in declared order; unlisted folders are appended alphabetically.

```js
// app/docs/_meta.js
export default {
  index: "Introduction",
  "getting-started": "Getting Started",
  "core-concepts": "Core Concepts",
  packages: "Packages",
  reference: "Reference",
};
```

<Callout type="tip" title="Labels and order in one place">
  A string value is the label (`"getting-started": "Getting Started"`). Omit a folder
  from `_meta.js` and it still appears — just alphabetically, using its frontmatter title or a humanized folder name.
</Callout>

### Groups with their own page

A folder with child folders is a group in the sidebar. When the folder also has its
own `page.mdx`, list it as `index` in that folder's `_meta.js`:

```js
// app/docs/deployment/_meta.js
export default {
  index: "Overview",
  build: "Production Build",
  server: "Server Setup",
};
```

- **The heading stays a label.** "Deployment" is not a link; it only groups its pages.
- **The folder's page is a child.** It is listed as "Overview", in the declared order, at the folder's URL (`/docs/deployment`).
- **Without `index`,** the folder's page is the heading's link.

### Route groups in the sidebar

A [route group](/docs/routing/route-groups) folder, such as `(guides)`, is a sidebar
heading over its pages, and their links have no group in them:

```js
// app/docs/_meta.js
export default { index: "Introduction", "(guides)": "Guides", "(reference)": "Reference" };
```

- **Label:** the `_meta` entry, or the folder name without parentheses.
- **URLs:** `app/docs/(guides)/install/page.mdx` is `/docs/install`, in the sidebar, breadcrumbs, last-updated dates, feeds and `llms.txt`.

## Mobile navigation

On screens narrower than **768px** the sidebar doesn't fit beside the content, so it
becomes an **off-canvas drawer**. A hamburger button appears at the start of the navbar
and slides the sidebar in over a dimmed backdrop:

- It shows **only** on small screens, and **only** on pages that have a sidebar (docs
  and other `DocsLayout` sections) — never on a plain marketing page.
- The drawer **locks page scroll** while open and closes on navigation, <kbd>Esc</kbd>,
  a tap on the backdrop, or a resize back up to desktop width.
- `prefers-reduced-motion` disables the slide animation.

To keep the bar uncluttered on phones, the navbar also **collapses to a single row** —
brand on the left, a compact action cluster (search · GitHub · theme) on the right — and
its **top-level links move into the drawer**, above the section tree, so the whole
navigation is reachable from one place.

This is automatic — there's nothing to configure. On desktop the sidebar is the sticky
column and the top-level links sit in the navbar, as usual.

<Callout type="note" title="Works across layouts">
  The burger lives in the navbar and the drawer in the docs grid, which may be separate
  layouts. They stay in sync through a small global toggle and an `afw:sidebar` event,
  so the button's open/closed state is always correct.
</Callout>

## Page frontmatter

Per-page frontmatter controls how a page shows up:

| Key | Effect |
| --- | --- |
| `title` | Default sidebar label and breadcrumb (unless `_meta` or `sidebar_label` overrides it), plus document title. |
| `description` | Meta description for SEO. |
| `sidebar_label` | Overrides `title` for the sidebar; `_meta` labels take priority over both. |
| `order` | Included in generated navigation data; the default sidebar order comes from `_meta.js`, then alphabetical folder names. |
| `lastUpdated` | Override the "Last updated" date, or `false` to hide it on this page. |

## Last updated & Edit this page

Turn on **`docs.lastUpdated: true`** to show a "Last updated on …" line at the foot of
each page in every `DocsLayout` section (`/docs`, `/api`, and any other section folder).
The date comes from the file's **last git commit** — no manual bookkeeping, and it
reflects when the content actually changed.

Pair it with **`docs.repoUrl`** (your GitHub repository root, not a specific file) to
also render an **"Edit this page"** link beside the timestamp. The link targets
`<repoUrl>/edit/main/<path-to-source>` for the current route's `page.mdx` / `page.jsx`.

```js
export default defineDocsConfig({
  docs: {
    // …
    repoUrl: "https://github.com/org/repo",
    lastUpdated: true,
  },
});
```

With `lastUpdated: true`, the `afwDocsPlugin` build plugin emits the dates and
per-route source paths. Edit links require the
generated source path and `repoUrl`; they can still appear when a page's timestamp
is hidden with `lastUpdated: false`.

The same SSG build also emits an Open Graph `article:modified_time` meta tag per page,
so crawlers see the modification date.

<Callout type="info" title="Overrides and git history">
  A `lastUpdated:` value in a page's frontmatter pins the date (any `YYYY-MM-DD` works);
  `lastUpdated: false` hides the line for that page. If the file isn't in git history
  (e.g. a shallow CI clone — use `fetch-depth: 0`), the line is simply omitted; there is
  no file-mtime fallback, since mtime doesn't track content changes.
</Callout>

The blog supports the same option: `blog.lastUpdated: true` adds the line to a post
only when it was edited *after* its publish date, so a fresh post stays clean.

## Build plugins

Add one entry to the top-level `plugins` array in your existing `esdev.json`,
alongside the AFW compiler/routes and site-output plugins (esdev 0.27 or later):

```json
{
  "plugins": [
    { "module": "@opentf/esdev-plugin-afw", "options": { "mode": "ssg" } },
    { "module": "@opentf/afw-docs/build", "export": "afwDocsPlugin",
      "options": { "appDir": "app" } }
  ]
}
```

`afwDocsPlugin` reads `afw.config.js` and enables what it asks for:

- `docs` → the sidebar navigation.
- `blog` → the post list, from `blog.dir`.
- `lastUpdated` → the per-page dates and edit links.
- Always → code-fence highlighting of compiled `.md`/`.mdx` pages.

Keep your build targets and `siteOutputPlugin` entry from
[Static Generation](/docs/deployment/static-generation). The individual plugins
(`docsNavPlugin`, `blogPostsPlugin`, `lastUpdatedPlugin`, `codeHighlightPlugin`) are
still exported for custom setups.

### With Vite

In the Vite + Node workflow, one plugin does all of this. It reads the same
`afw.config.js`, generates the sidebar, post list and last-updated data, and after
the prerender writes the search index, the blog feeds and `llms.txt`:

```js
// vite.config.js
import afw from "@opentf/vite-plugin-afw";
import afwDocs from "@opentf/afw-docs/vite";

export default { plugins: [afw({ mode: "ssg" }), afwDocs()] };
```

Test search with `vite build` and `vite preview`.

## Search

Set `docs.search: { provider: "afw" }` and configure `siteOutputPlugin` after
prerendering. It runs the native `afwc docs index` command and writes `_search/`
into the static output. `DocsLayout` and `BlogLayout` mark their article content
for indexing; navigation and page chrome are excluded.

The search UI loads that index in the browser. Test with a release build and
`esdev preview`; development does not regenerate the release index. See
[Static Generation](/docs/deployment/static-generation#search-and-other-generated-files).
